## 2. 問題清單（依嚴重度）

沒有發現會讓現有使用者資料損毀或頁面打不開的問題。下面 6 項「中」建議在提交 1.4.0 之前或 2.0 之前修；其餘可以排進之後的修訂版。

### 中

**R-01　線上版部署新版後，舊分頁要的舊檔會拿到網頁本身，而且被永久快取**
- 位置：`scripts/web/sw.js:46-60`（`/assets/` 快取優先，只檢查 `res.ok`）。
- 證據（實測，本機 `preview:web`）：在被 service worker 控制的頁面請求一個不存在的 `./assets/three-OLDHASH00.js`，伺服器回 200、`text/html`（退回首頁），這筆回應被寫進 `sf-assets-v1`。
- 證據（推論）：Cloudflare Pages 在沒有 `404.html` 時也會把找不到的路徑退回首頁，所以實際部署會有同樣的行為（沒有在真實部署上驗證）。
- 影響：使用者開著舊分頁時你部署新版，之後他第一次用到 3D、某個樂器或背景執行緒，動態載入會失敗；那個網址還會一直留著錯的內容。3D 會停在占位卡，聲音會退回合成音色或失敗。
- 重現：`npm run build:web` → `npm run preview:web` → 開頁面等 service worker 啟用 → 主控台 `fetch('./assets/x-OLD.js')` → 看 `caches`。
- 建議：`/assets/` 的回應要檢查 `content-type` 不是 `text/html` 才快取、才回傳（否則回 404）；`dist-web` 加一個 `404.html`；動態載入失敗時提示「有新版本，請重新整理」。

**R-02　「墊底」與「平穩」的琶音收小，在精修開啟（預設）時沒有效果**
- 位置：`src/audio/arrange.ts:121`（墊底時琶音 ×0.75）、`arrange.ts:39`（平穩主體琶音 0.6）對上 `src/audio/gm.ts:731`（每一軌的響度對齊到固定目標）。
- 證據（實測，Node 單獨渲染琶音軌量「有聲部分」響度）：

  | 曲風 | 精修開：無墊底 → 墊底 | 精修關：無墊底 → 墊底 |
  | --- | --- | --- |
  | house | −34.9 → −34.9（差 0.0 dB） | −32.5 → −35.0（差 −2.5 dB） |
  | kpop | −34.4 → −34.4（0.0） | −32.8 → −35.3（−2.5） |
  | cinematic | −34.7 → −34.7（0.0） | −33.8 → −36.3（−2.5） |

- 原因：編排把整軌的力度一起調小，精修再把整軌拉回目標電平，剛好抵銷。鼓有另外減 3 dB（`gm.ts:731`），琶音沒有。
- 影響：墊底模式的琶音沒有照設計讓位給口播。
- 建議：把「這一軌整體要比目標低多少」從編排帶到渲染（例如 `Track.trim`，單位 dB），精修對齊時加上去；不要靠力度傳遞整軌音量。

**R-03　長配樂的記憶體：快取、分軌 ZIP、整首導出都沒有上限**
- 位置：`src/audio/engine.ts:163-182`（保留最近 4 首的 PCM）、`engine.ts:362`（試聽再複製一份）、`src/audio/files.ts:28-76`（分軌全部放在記憶體，`zipSync` 再複製）、`src/components/Modals.tsx:338`（GIF 超過 15 秒只有文字提醒）、`src/lib/exporter.ts:233-244`（PNG 序列全部放記憶體）。
- 證據（實測，Node）：179.2 秒的配樂，PCM 60.3 MB；每一軌的 16 位元 WAV 30.1 MB；渲染 4.5～7.4 秒（pop 5 軌 3,205 個音、cinematic 6 軌 768 個音）。
- 證據（推論，算術）：
  - 來回切 4 個曲風的最長配樂：快取 4 × 60 MB＋播放用的緩衝 60 MB＋試聽緩衝 60 MB ≈ 360 MB（主執行緒）。
  - 6 軌分軌：WAV 共 181 MB，`zipSync`（不壓縮）再一份、Blob 再一份，高峰約 540 MB，而且 `zipSync` 是同步的，會卡住介面。
  - 「整首」導出 180 秒 PNG 序列（24 fps＝4,320 張）或 GIF：全部先放記憶體，1080p 下會到幾 GB，分頁會被瀏覽器關掉。
- 影響：手機與記憶體小的電腦上，分頁可能當掉；沒有實際在裝置上重現。
- 建議：渲染快取改成「總秒數上限」（例如合計 240 秒）而不是固定 4 筆；分軌改用 fflate 的串流 `Zip`，一軌做完就釋放；導出視窗在「張數 × 像素」超過門檻時擋下 GIF／PNG 序列並建議 MP4。

**R-04　配方碼可以繞過「最多混 6 個風格」的上限**
- 位置：`src/store/sanitize.ts:12-21`（沒有數量上限）對上 `src/store/store.ts:107`（`MAX_PER_KIND = 6` 只在介面加入時檢查）；`store.ts:325`、`store.ts:377-391`（本機存檔也一樣）。
- 證據（實測）：配方碼帶 136 個圖像風格 → `importCode` 回傳成功、`v` 有 136 個；「混合配方」區塊高度從 130 px 變 2,523 px，舞台被擠出畫面。混合運算本身只要 0.17 ms，效能不是問題。
- 影響：一個刻意造出來的連結會把對方的版面弄壞，而且會寫進本機存檔（要自己一個個移除或清除資料）。
- 建議：`sanitizeSels` 加 `max` 參數，超過就截斷。

**R-05　背景執行緒沒有取消機制，過期的渲染會排隊**
- 位置：`src/audio/renderClient.ts:74-94`、`src/audio/renderWorker.ts:21-30`、`src/audio/engine.ts:185-219`。
- 證據（推論）：背景執行緒裡的渲染不讓出執行權（`yieldEvery: false`），所以工作是一個接一個做。引擎只用 `token` 丟掉過期的結果，沒有通知背景執行緒停手。
- 證據（實測）：最長配樂一首要 4.5～7.4 秒（Node；瀏覽器裡沒有量）。
- 影響：在配樂模式下連續換 3 次曲風（每次間隔超過 320 毫秒的防抖），最後那首要等前面兩首做完，可能等 10～20 秒；介面不會卡，但「渲染中」會掛很久。
- 建議：工作帶世代編號，新工作進來時把還沒開始的舊工作從佇列移除；或渲染迴圈每一軌檢查一次「是否已作廢」。

**R-06　線上版只開過一次就離線，會少一個必要的程式檔**
- 位置：`vite.config.ts:51`（殼清單只收 `assets/index-*.js|css`）。
- 證據（實測）：第一次造訪後列出所有快取，`/assets/util-Cjas2niN.js` 不在任何快取裡；而主程式第一行就靜態匯入它。
- 證據（推論）：Cloudflare 上 `_headers` 給了一年的 `immutable`，瀏覽器的 HTTP 快取多半還是會供應這個檔，所以實際多半開得起來；換到沒有設快取標頭的主機，或 HTTP 快取被清掉，離線就會白屏。**沒有實際斷網測試**（內建瀏覽器做不到）。
- 建議：殼清單改成「`index.html` 參照到的所有檔案」（Vite 的 `bundle` 裡 `isEntry` 的檔案與它的靜態 `imports`），不要用檔名規則猜。

**R-07　背景執行緒第一次建立時的競爭**
- 位置：`src/audio/renderClient.ts:19-50`。`tried = true` 設在 `await import(...)` 之前，第二個同時進來的呼叫會拿到還是 `null` 的 `worker`，退回主執行緒渲染。
- 證據：推論。會發生在「背景音樂與試聽幾乎同時開始」的第一次；結果只是那一次卡一下。
- 建議：快取的是 Promise（`workerP ??= create()`），不是布林值。

**R-08　網頁本身的快取沒有檢查回應**
- 位置：`scripts/web/sw.js:33-43`。任何導覽回應都會被存成 `./index.html`：錯誤頁（5xx）、被登入頁攔截的回應都會。沒有 `e.waitUntil`，寫入可能還沒完成 service worker 就被收掉。沒有逾時：網路很慢但沒斷時會一直等。
- 證據：推論。
- 建議：只存 `res.ok && res.type === 'basic'` 而且是 HTML 的回應；`e.waitUntil(寫入)`；網路超過 3 秒就先給快取。

**R-09　帶雜湊的檔案快取只增不減**
- 位置：`scripts/web/sw.js:7`、`:19-26`。`sf-assets-v1` 從不清理；每次部署主程式（約 1 MB）、3D（0.7 MB）換雜湊就多一份。
- 證據：推論。
- 建議：建置時把這一版的檔名清單寫進 `sw.js`，啟用時刪掉清單以外的項目。

**R-10　導出時音樂可能靜靜地消失**
- 位置：`src/audio/engine.ts:192-219`（`token` 不符回傳 `null`）、`engine.ts:234-243`、`engine.ts:442-455`（`got?.pcm ?? null`）。
- 證據：推論。導出等待渲染期間如果計畫又變了（例如視窗量到新比例、主題重新載入），這次的渲染會被作廢，`exportMix` 拿到 `null` 就照樣混出**沒有音樂**的音軌，不報錯。
- 建議：`exportMix` 在使用者要音樂卻拿不到時丟出錯誤（「音樂還在準備，請再試一次」），不要靜靜輸出無聲。

**R-11　GIF 的播放速度和設定的幀率不一致（1.4.0 之前就有）**
- 位置：`src/lib/exporter.ts:139`（`delay = 1000 / fps`）；`node_modules/gifenc/src/index.js:100`（`Math.round(delay / 10)`，GIF 的延遲單位是 1/100 秒）。
- 證據：推論（讀函式庫原始碼）。24 fps → 4 單位＝25 fps（快 4%）；30 fps → 3 單位＝33.3 fps（快 11%）；60 fps → 2 單位＝50 fps（慢 17%）。只有 20、25、50 fps 是準的。
- 影響：GIF 的長度和音樂、和 MP4 對不上。
- 建議：GIF 的幀率選項只給 10、12.5、20、25、50；或用誤差累進，讓每幾格多一個單位，總長度維持正確。

**R-12　WebM 是照真實時間錄的，畫面慢就會和聲音錯開**
- 位置：`src/lib/exporter.ts:199-231`。
- 證據：推論。聲音用 `AudioContext` 即時播放，畫面用 `setTimeout` 追進度；單格畫超過 1/fps 秒（4K、3D、重的後期）或分頁被切到背景（計時器被降到 1 秒一次）時，畫面會落後聲音。
- 建議：介面上註明「WebM 導出時請停在這個分頁」；偵測到落後超過 2 格就提示改用 MP4。長期可以改用 WebCodecs 加 WebM 封裝，和 MP4 一樣離線逐格。

- 每幀耗時只量了 flat 風格、640×360、30 格平均；沒有量帶後期特效、1080p、p95，也沒有量 3D 主體。音樂視覺化在 3,000 個音符下的數字沿用上個 session 的紀錄，這次沒有重量。
- `?full=1`（15,210 次）這次沒有重跑；`audio:sweep` 也沒有重跑。
- 背景執行緒排隊（R-05）沒有在瀏覽器裡實際重現等待時間。
